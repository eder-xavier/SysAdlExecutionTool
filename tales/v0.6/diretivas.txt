Estas diretivas devem ser consideradas em todos os prompts que você for executar.

Diretivas gerais:

0) Estamos trabalhando exclusivamente na pasta /tales/v0.6
1) A solução deve ser sempre genérica, independente do arquivo sysadl usado como exemplo. 
2) Não devem existir hardcodes
3) Estamos trabalhando em um sistema de transformação de arquivos .sysadl em arquivos executáveis .js. Esta transformação é feita pelo transformer.js
4) As classes base para a transformação e definições estão na pasta sysadl-framework
5) Na transformação, são gerados 2 arquivos baseados em um arquivo.sysadl, por exemplo: 1) arquivo.js (modelo estrutural) 2) arquivo-env-scen.js (ambiente e cenários)
6) O simulador integrado é o arquivo SysADLSimulator.js. Ele deve executar os arquivos .js gerados e gravar um log na pasta /logs. O environment-simulator.js é legado e não deve ser mais utilizado.
7) Este log deve mostrar as interações entre cada EnvComponent do ambiente, considerando o sistema modelado na execução dos cenários. A interação com o sistema modelado se dá pela associação de um EnvComponent com uma instância de component via BoundaryComponentExtension e environmentConfiguration.
8) No geral, os modelos funcionam assim: o environmentConfiguration (embutido dentro dos EnvComponents) configura instâncias que serão executadas nos cenários. Ele instancia sub-EnvComponents, cria EnvConnectors com bindings, e define envDelegations entre níveis hierárquicos. A relação com o sistema modelado se dá via BoundaryComponentExtension (que atribui envPorts a boundary components) e via components dentro do environmentConfiguration. O que "comanda" a execução é a definição em ScenarioExecution, que chama ScenarioDefinitions, que chama SceneDefinitions. As cadeias de eventos são definidas por ON/THEN/SEND clauses nas EnvActivities (dentro de EnvActivitiesDefinitions). 
9) Resumindo a cadeia de execução (nova gramática):
ScenarioExecution 
    ↓ chama (parallel ou sequencial)
ScenarioDefinitions 
    ↓ chama  
SceneDefinitions (com pre/postconditions)
    ↓ executa
EnvActivitiesDefinitions (cadeias ON/THEN/SEND)
    ↓ usa
environmentConfiguration (instâncias de EnvComponents + BoundaryComponentExtension bridges)
    - EnvComponents definem os elementos do ambiente (com envPorts e properties)
    - BoundaryComponentExtension conecta envPorts aos boundary components do sistema
    - EnvConnectors com bindings conectam envPorts de EnvComponents a ports de system Components
    - envDelegations conectam portas entre níveis hierárquicos
10) Nenhuma alteração deve ser feita nos arquivos js gerados. Caso eles precisem de alguma mudança, as mudanças devem ser aplicadas no transformer.js
11) O objetivo deste sistema todo é validar os models .sysadl através da simulação, através dos arquivos .js transformados. 
12) Os arquivos .sysadl, sysadl.peg, sysadl-parser.js nunca devem ser modificados, a não ser com autorização explícita.
13) Sempre que eu te pedir para transformar um arquivo .sysadl, você deve utilizar o transformer.js com os parâmetros correspondentes, ou o arquivo transform_all.sh, que já faz o trabalho completo.
14) Sempre que eu te pedir para simular, você deve utilizar o SysADLSimulator.js com os parâmetros necessários.
15) Todo arquivo de teste deve ser colocado na pasta /tales/v0.6/test
